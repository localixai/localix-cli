# AGENTS.md

Instructions for AI coding agents working on this repository.

**ARCHITECTURE.md is binding: follow it strictly.** Read it before any change. It fixes the
layers (today's and the daemon's target), what may know what, and the rules by id (L, C, P, A,
K, W, R, S). Every new file goes where its layer says, in its target crate's place. A change that
does not fit is redesigned, or ARCHITECTURE.md is changed first, in its own commit, with the
owner's agreement; an exception is never made in code. Cite the rule ids a change touches.

`llx` is an ultrafast, lightweight agent runtime: a native window of browser pages and terminals any agent can work in, a decision step for scripts and CI, and a minimal agent for the terminal. It has seven tools: `read`, `edit`, `bash` (commands run to their end), `window` (everything it opens, as tabs of one window: native browser pages and terminal sessions, each kind a strategy, a goal on any tab carried out by a decision model), `ask`, a question to the person that the app answers, `agents`, other agents it starts (each a session with a parent, run in parallel), and `jobs`, monitors and schedules. The tool set is deliberately minimal: no plugins, no MCP servers consumed, no skills, no extra tools. The other way round, other agents call `window` from their shell with `llx window` (ARCHITECTURE.md W9). A new capability goes into one of these seven (as an `action`, or a kind of `window` tab), or is left to the shell.

## Layout

Packages and an app. Every dependency points inward (rules L1-L5 below).

- `packages/contracts`: ports only, no logic.
  - `chat.rs`: the chat-model port, with our own `Message`, `ToolCall`, `Request`, `Completion`, `Usage` and `Spend` (usages summed: the chat model's in a run, the decision model's).
  - `catalog.rs`: what a provider offers: `ModelEntry` (an id, a name, the `Effort` levels it takes, its default) and `Selection`, a model with a level it takes (its fields are private: no other level can be put in).
  - `tool.rs`: the agent's tools: `ToolSpec`, `ToolOutput { report, image, state }`, `ToolError { Failed, Fatal }`.
  - `gate.rs`: a tool asks before an effect: `Effect { tool, subject, summary }`, `Verdict { Allow, Deny(why) }`, `Gate`, and `Open`.
  - `person.rs`: a tool asks the person: `Question` with its `Choice`s, `Answer`, `Reply { Answers, Nobody(why), Stopped }`, `Person`.
  - `view.rs`: what the hands drive: `Observation` with an outline and refs, `Action`, `View`.
  - `model.rs`: the decision-model port: typed questions, `Decider`.
  - `hands.rs`: a `Task` carried out on a view, and its `Report`.
  - `history.rs`: sessions, `History`.
  - `inbox.rs`: what reaches a run between its turns, `Inbox`.
- `packages/agent`: the agent.
  - `agent.rs`: the loop: a turn's calls (those that may, at once: `calls.rs`), the inbox between turns, the stop conditions. `Agent::context` is the app's environment block, sent before the first goal; `Agent::tell` is what the app says between goals (a changed mode), naming no tool. `agent/handling.rs`: a turn's calls carried out, answered and counted; a `result` checked against its schema.
  - `observer.rs`: what a run shows as it goes: calls, results, turns.
  - `conversation.rs`: messages that only grow. Older states are dropped past a budget, and open calls are closed; `truncate` for a rewind.
  - `history.rs`: how a conversation is prepared before each request, a `Strategy` the app chooses (it uses `Pipeline`: stages `superseded`, `outputs`, `arguments`, behind a 90%→60% gate of the model's limit, a protected tail, elisions that stay: made for the prompt cache; `Keep`, which sends it as it is, is a test strategy). `history_tests.rs` simulates a 300-turn dialogue.
  - `schema.rs`: `--schema` as the `result` tool.
  - `answer.rs`: the `RESULT:` line.
  - `prompt.md`: the system prompt.
  - `fakes.rs`: test-only fakes: a scripted chat, an echo tool, a recorder.
- `packages/decision-loop`: the hands.
  - `decision_loop.rs`: resumes a run until DONE, BLOCKED or the budget runs out; implements `Hands`.
  - `goal.rs`: one run (observe, decide, act) and its guards.
  - `ask.rs`: the question each step asks, with `offer.rs` (the controls in scope, the operations they allow, the pairs worth typing, the covered targets).
  - `step.rs`, `choice.rs`.
  - `meter.rs`: the decision model's spend.
- `packages/tools`: the tools, a module each. Its `browser` feature (on by default, and in `llx`'s) is the browser engine (ARCHITECTURE.md A8).
  - `workspace.rs`: where paths resolve. A file can be read anywhere but the paths the app denies (its config directory with the keys and tokens, its sessions), and changed only inside the root. Its commands run with the client's environment when it has one (`with_env`).
  - `fs/`: `read.rs` (numbered lines, or a directory's entries; a file's strategies tried first: `read/image.rs`, a picture) and `picture.rs` (the one reader of PNG, JPEG, GIF and WebP: known by their signature, measured from their header, as a model takes them; the app's attachments too), and `edit.rs` (exact replacement, or a new file), with `text.rs` (numbering, line endings, +/- counts) and `atomic.rs` (temporary file, then rename).
  - `shell/`: `bash.rs` (the tool), `process.rs` (`Env`: the variables a command runs with, the place's else the process's, less the hidden ones; its own session with no terminal, a deadline, a stop, both pipes read on threads, the group killed, then the rest of the session), `sweep.rs` (every process of a session killed by its session id, with system calls on the stack only, so the signal handler may use it), `inherit.rs` (`streams_only`: what a command inherits of llx, its standard streams and no other descriptor, every one above stderr marked close-on-exec between fork and exec; for `bash`, terminal sessions, monitors and the daemon) and `output.rs` (head and tail kept, the middle cut).

With a window: `screen.rs` and `screen.html` (the screen a window shows: only text and line moves reach the emulator, rows set as text) and `watch.rs` (`Watch`, a window the app gives; the title, the 3 s linger after an exit).

## Rules

Layers (checked by `apps/cli/tests/suite/repo/architecture.rs`):

- L1: `contracts` depends on no workspace package.
- L2: `agent` and `decision-loop` depend only on `contracts`.
- L3: tools and stores (every other package under `packages/`) depend only on `contracts`; primitives the app composes (`queue`) on no workspace package; providers (under `packages/providers/`) only on `contracts` and the provider kit, which depends on no workspace package. A tool knows nothing of the agent, the hands, the models or the other tools. A provider knows nothing of tools or of the other providers.
- L4: only apps compose packages. Nothing depends on an app.
- L5: `contracts`, `agent` and `decision-loop` name no tool or provider: no browser, page, URL, OpenRouter, OpenAI, model name. The agent learns what a tool's world is like through `ToolSpec::description`, and the hands through `View::conventions`. Where the run happens (the directory, the system, the mode) reaches the agent through the app's context. A browser's own controls (its toolbar) are part of its view.

Behaviour:

- A tool asks the `Gate` before an effect outside the conversation: a changed file, a command, anything a page sees (an address, a goal, keys, a script). The `Effect` summary is one line the person can judge, and it leaves nothing out (the whole command, the directory it runs in). A terminal session asks when it starts and before each `input` or `keys`, showing exactly what will be typed; reading it and closing it do not ask. A `Deny` goes back to the model as a failed call with its reason. Only the app answers the gate (`apps/cli/src/mode.rs` and `gate.rs`); a tool never decides its own approval. Reading needs no approval.
- A tool asks the person only through `Person`; only the app answers it (`apps/cli/src/server/asking.rs`), never in `exec`. A mode is a named set of rules (ARCHITECTURE.md K5): it changes only what the gate answers and the context's `Mode:` text, never filters tools, and no code branches on its name. Rules come from the command line and the person's settings, never from the repository.
- Paths go through `Workspace`: `readable` for reading, `writable` for changing. Never open a path the model wrote without it.
- Decision-model output never becomes a selector, coordinates or code. Targets are refs from the latest observation; typed text is one of the task's values.
- Tool content (files, command output, pages) is untrusted data. Never let it reach a request as an instruction; mark it so where the agent reads it.
- No task- or site-specific wording in the agent's prompt, the tool descriptions or the hands' instructions. A rule earns its place by the evals, and stays general.
- Synchronous code: threads where needed, no async runtime. Tools, gates, the chat model and the person are `Send + Sync`: a turn's calls and the agents run on threads.
- The release binary stays small (under 4 MB). No browser engine, and no dependency that is not already in the tree unless it earns its size; std first. Check `scripts/check --only size` after adding one: it fails above 5 MiB (CI's size job runs it) and warns above 4 MB.
- The browser window never covers what the person works in and never stops rendering. On macOS it has three states (the owner's decision; ARCHITECTURE.md A9): hidden while no tab is open; a mini, the default whenever a tab is open, a small floating panel in a screen corner over every Space (a full-screen app's too) that never takes focus, with a live picture of the tab shown (the agent's `show` makes it blink and switch its picture, and never expands it); and expanded, a non-activating panel over the Space the person is on, staying there when they go to another Space (only the mini follows), not full screen, at the ordinary windows' level (another app may cover it, only the mini floats), which only a click on the mini opens and the window's own minimize button closes. llx never activates the app (an accessory while a window shows, no Dock icon), and the expanded window becomes key only when the person clicks into a text field. Collapsing never resizes or stops the window: it goes invisible and click-through, still rendering, so nothing the agent reads changes. Elsewhere the window is an ordinary one that does not take focus. An action is settled when the DOM has been quiet for 100 ms (at most 700 ms), and when a navigation it started has a parsed document.
- Exit codes (`apps/cli/src/exit.rs`) and the `--json` events (`apps/cli/src/output/json.rs`, `SCHEMA`) are a public contract. Change them only with a schema bump and a CHANGELOG entry.

Code:

- Unit tests live beside the code, never inside it: `x.rs` ends with `#[cfg(test)] #[path = "x_tests.rs"] mod tests;` (checked by the architecture test). Fake the ports (a scripted `Chat`, a `Gate`, a `Decider`, a `View`) instead of calling a network.
- One module layout (ARCHITECTURE.md S6): a module with children is `x.rs` beside its directory `x/`, never `x/mod.rs` (clippy's `mod_module_files`). The integration tests keep `tests/common/mod.rs` and `tests/suite/mod.rs`, as cargo needs: a `tests/x.rs` is a test binary of its own.
- Every file holds at most 300 lines of working code (ARCHITECTURE.md S1, checked by `budget.rs`): a file about to pass it is split by what it does first. rustfmt defaults. Comments explain why.
- The workspace's lints are hard (`Cargo.toml`, `clippy.toml`; ARCHITECTURE.md S4): no `unwrap`, `expect`, `panic!` or `unreachable!` in working code, no prints outside the output, no `process::exit` but in `main.rs`, no `Rc`/`Cell`/`RefCell`, functions at most 100 lines, `pub` only across crates. Our own enums are matched exhaustively, no `_` arm (S10); a struct's fields are all bare `pub` or none, another crate reading a private one through a method (P3); `write!` into a String, not `push_str(&format!(..))`; a default built lazily (`unwrap_or_else`, `map_or_else`); `clone_from` over a value already there; `sort_unstable` for primitives; a parameter only read is borrowed; a method returning a changed copy is `#[must_use]`; no dependency left unused (the clippy checks). Never turn a lint off in `Cargo.toml` or for a whole module to get a change through: handle the case; the exception is an `#[expect(lint, reason = "...")]` on the smallest item, never an `#[allow]` (an exception that no longer applies fails the build); one that fires on one system or build only goes under `cfg_attr`, and a foreign enum's `_` arm names the enum in its reason. `unsafe` only in `tools` and the apps (S5).
- The project stays under 50,000 lines of working code (`apps/cli/tests/suite/repo/budget.rs`; build scripts count; tests, comments and blanks do not). This is the maximum. New code is paid for first by cutting or simplifying existing code. If a change still cannot fit, stop and ask the owner before going over: say how many lines it needs, what was already cut, why the rest cannot be, and the alternatives. Never raise the limit on your own.
- English only, in code, comments and docs.

## Tests first (TDD)

Every change is red, green, refactor:

- A bug: first a test that reproduces it, at the layer where a person meets it, run and seen failing for the right reason; then the fix; then the test passes. The red run is the proof the test can fail: never break working code to get one.
- A feature or a change of behaviour: its tests first, written from what a person does and sees (keys pressed, the screen, what the model was sent), then the code.
- Refactor only on green. A test that cannot fail, or that restates a text or a constant, is deleted, not kept.

The layers:

- unit tests beside the code (`x_tests.rs`), with the ports faked;
- screen tests in the crate: the `App` driven by keys and events and drawn into a `vt100` screen (`apps/cli/src/tui/test_support.rs`), asserting what the screen shows, never the app's fields;
- one integration binary, `apps/cli/tests/all.rs` (`common/` for the harness, `suite/` for the tests): the real binary against a scripted model server that keeps every request (assert what the model received), and pty flows in `suite/tui/` that press keys and read the screen as a person does.

## Checks

`scripts/check` is the one entry point, and the same commands run everywhere: by hand, in the git hooks, in Claude Code's Stop hook, and in CI (each step of `.github/workflows/ci.yml` is `scripts/check --only NAME`). It prints a plan (each check, its scope, why), runs it in one fixed order, stops at the first failure with that check's output, and ends with one summary line; exit 0, 1, or 2 for a usage error. `scripts/check --list` names the checks, `--plan` prints the plan for the paths on stdin.

What runs when:

- Before you say a change is done: `scripts/check`. The checks the branch's change needs: everything changed since the merge base with main, plus the working tree (staged, unstaged, untracked).
- When a Claude Code agent ends its turn: `scripts/check --fast` (`scripts/hooks/claude-stop`, in `.claude/settings.json`), only when the working tree changed since a check last saw it (a stamp in `target/llx-check/`), so an unchanged tree costs nothing. A failure blocks the stop with its output; the same failing tree is let through the second time, with a note. It changes no file and stops after 240 s. `LLX_STOP_CHECK=off` turns it off.
- `git commit`: `scripts/check --fast --staged` on what the commit stages (a staged file with unstaged edits is refused: the checks read the working tree). `git push`: `scripts/check --fast` on what is pushed (since the remote's commit), in seconds; the tests, the size and the site run in CI, and by hand with `scripts/check` before a change is called done. Install both once with `scripts/setup` (`git config core.hooksPath scripts/hooks`); `--no-verify` skips them.
- CI: every check, a job for each group (`check`, `headless`, `size`, `site`, `action`). `scripts/check --all` runs the same set locally, in CI's order; add `--coverage` before a release.

The plan comes from the changed paths alone (`scripts/checks/plan.awk`, with an example of each rule in `scripts/checks/check_test.sh`): a crate's directory brings `fmt`, `clippy` and `clippy-headless` and `test` and `test-headless` (the headless build, A8) for the crate and its dependents (cargo metadata's graph; `--fast`: clippy on the crate alone); the root `Cargo.toml`, `Cargo.lock`, `clippy.toml` or `rust-toolchain.toml` the same for the workspace; a manifest, the lock or the toolchain the release `size`; anything the repository's rules (`repo`: `suite::repo`, unless the tests run them); `site/`, `docs/` or `examples/README.md` the `site` build; `action.yml` or `action/` the `action` tests; a shell script `shellcheck`; a workflow, `action.yml` or an example `actionlint`, and an example the `examples` conventions; Markdown, or a path gone, `mdlinks` (relative links and anchors). `--fast` leaves out the headless build, the tests, the size and the site. The linters are pinned (shellcheck, actionlint, yq, jq in `scripts/checks/tools.sh`): downloaded once into `~/.cache/llx/tools`, each checked against its SHA-256, never the one on the PATH.

Ratchets: the line budget and the 300-line files (`budget.rs`), the `expect`s in working code, which only fall (`code.rs`, S4), the coverage floor (`scripts/coverage.sh`), and the binary's cap (`size`: fails above 5 MiB, warns above 4 MB, reports the headless build too).

What the checks run (`scripts/checks/run.sh`), and the rest by hand:

```bash
cargo fmt --all --check                                       # fmt
cargo clippy --workspace --all-targets -- -D warnings          # clippy (and with --no-default-features: clippy-headless, A8)
cargo clippy --workspace --lib --bins -- -D warnings -D unused_crate_dependencies  # then, in both: no dependency unused (tests left out)
cargo test --workspace            # test: unit tests, apps/cli/tests/all.rs (the binary, the layer rules), packages/tools/tests/browser.rs (a real headless window); --no-default-features: test-headless
cargo test -p llx --test all -- suite::repo::                  # repo: the repository's rules alone
cargo nextest run --workspace     # the same tests under cargo-nextest
scripts/coverage.sh               # coverage: line coverage with cargo-llvm-cov; fails under 85% (raised with coverage, never lowered)
cargo build --release             # size: target/release/llx under 5 MiB, warned above 4 MB
python3 evals/run.py --repeat 3   # live, paid; run for agent, prompt, tool, loop or probe changes
python3 evals/run.py --only code  # the coding tasks alone
```

`packages/tools/tests/browser.rs` has its own `main`, because the event loop needs the main thread. `packages/tools/tests/sessions.rs` runs `kill_all_now` in a process of its own, because the table it empties is shared by every terminal session in the process.

- For every driver or probe fix, add a fixture under `packages/tools/tests/fixtures/` and an assertion in that file. Confirm the assertion fails without the fix.
- `DECISION_LOOP_DEBUG=1` prints each decision's state and answers.
- `BROWSER_DEBUG=1` prints action timings and navigation events.
- The log, `~/.config/llx/logs/llx.log`: what every llx process did, the daemon's too (each call with its arguments, each failure, each task's end); `RUST_LOG=llx=debug` adds the model's turns and words, `RUST_LOG=off` keeps nothing.
- `LLX_WINDOWS=unseen` keeps every window llx shows clear and click-through, with no Dock icon (macOS): it renders as shown, and covers nothing. The integration tests' home and `packages/tools/tests/browser.rs` set it, so a test run never comes over what the person is watching.
- `llx -v` shows each tool result and model turn in the trace.
