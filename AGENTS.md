# AGENTS.md

Instructions for AI coding agents working on this repository.

**ARCHITECTURE.md is binding: follow it strictly.** Read it before any change. It fixes the
layers (today's and the daemon's target), what may know what, and the rules by id (L, C, P, A,
K, W, R, S). Every new file goes where its layer says, in its target crate's place. A change that
does not fit is redesigned, or ARCHITECTURE.md is changed first, in its own commit, with the
owner's agreement; an exception is never made in code. Cite the rule ids a change touches.

`llx` is an ultrafast, lightweight agent runtime: a minimal agent for the terminal, helpers on any model, and a decision step for scripts and CI. It has five tools: `bash` (commands run to their end: the model reads and searches with it and runs the checks, B1-B4), `apply_patch` (every file it adds, changes, deletes or moves, as a patch of free text, B5), `ask`, a question to the person that the app answers, `agents`, other agents it starts (each a session with a parent, run in parallel), and `jobs`, monitors and schedules. The tool set is deliberately minimal: no plugins, no MCP servers consumed, no skills, no extra tools. A new capability goes into one of these (as an `action`), or is left to the shell.

## Layout

Packages and an app. Every dependency points inward (rules L1-L5 below).

- `packages/contracts`: ports only, no logic.
  - `chat.rs`: the chat-model port, with our own `Message`, `ToolCall`, `Request`, `Completion`, `Usage` and `Spend` (usages summed: the chat model's in a run, the decision model's in `llx decide`).
  - `catalog.rs`: what a provider offers: `ModelEntry` (an id, a name, the `Effort` levels it takes, its default; `Effort::wire_name`, the spelling both providers send) and `Selection`, a model with a level it takes (its fields are private: no other level can be put in).
  - `tool.rs`: the agent's tools: `ToolSpec` (a name, a description, its `Input`: arguments' JSON Schema, or the Lark grammar of a text tool), `ToolOutput { report, state }`, `ToolError { Failed, Fatal }`.
  - `gate.rs`: a tool asks before an effect: `Effect { tool, subject, summary }`, `Verdict { Allow, ReadOnly, Deny(why) }` (`ReadOnly`: run where it can change nothing), `Gate`, and `Open`.
  - `person.rs`: a tool asks the person: `Question` with its `Choice`s, `Answer`, `Reply { Answers, Nobody(why), Stopped }`, `Person`.
  - `model.rs`: the decision-model port: typed questions, `Decider` (`llx decide`).
  - `history.rs`: sessions, `History`, whose `save` and `load` fail with `HistoryError`.
  - `inbox.rs`: what reaches a run between its turns, `Inbox`.
- `packages/agent`: the agent.
  - `agent.rs`: the loop: a turn's calls (those that may, at once: `calls.rs`), the inbox between turns, the stop conditions; an answer that does not say the goal is reached goes back (`GO_ON`), at most three times, never right after one. `Agent::context` is the app's environment block, sent before the first goal; `Agent::tell` is what the app says between goals (a changed mode), naming no tool. `agent/handling.rs`: a turn's calls carried out, answered and counted; a `result` checked against its schema.
  - `observer.rs`: what a run shows as it goes: calls, results, turns.
  - `conversation.rs`: messages that only grow. Older states are dropped past a budget, and open calls are closed; `truncate` for a rewind. A picture stays only when the person attached it.
  - `history.rs`: how a conversation is prepared before each request, a `Strategy` the app chooses (it uses `Pipeline`: stages `outputs`, `arguments`, behind a 90%→60% gate of the model's limit, a protected tail, elisions that stay: made for the prompt cache; `Keep`, which sends it as it is, is a test strategy). `history_tests.rs` simulates a 300-turn dialogue.
  - `schema.rs`: `--schema` as the `result` tool.
  - `answer.rs`: the `RESULT:` line.
  - `prompt.md`: the system prompt.
  - `fakes.rs`: test-only fakes: a scripted chat, an echo tool, a recorder.
- `packages/tools`: the tools, a module each.
  - `workspace.rs`: where paths resolve. A file can be read anywhere but the paths the app denies (its config directory with the keys and tokens, its sessions): an attached picture. Its commands run with the client's environment when it has one (`with_env`).
  - `fs/`: `patch.rs` with `patch/` (`apply_patch`: `tool.rs` the tool and its grammar, `run.rs` every file worked out and asked of the gate before any is written, a read-only verdict refused, `apply.rs` and `seek.rs` a hunk found by its lines and those around it, else the file's nearest lines given back), `atomic.rs` (a write as a temporary file renamed, line endings and permissions kept), `diff.rs` (what a change did, for the report), `picture.rs` (the one reader of PNG, JPEG, GIF and WebP: known by their signature, measured from their header, as a model takes them; the app's attachments).
  - `shell/`: `bash.rs` (the tool), `sandbox.rs` (`Scope { Open, ReadOnly }`, from a gate's verdict by `Scope::of`: a read-only command (B3) in the system's sandbox with a scratch `$TMPDIR` of its own, removed after; refused where none can be set up) with `sandbox/macos.rs` (Seatbelt: `sandbox-exec` with a profile closed by default) and `sandbox/linux.rs` (Landlock and a seccomp filter that refuses every socket, set between fork and exec after `no_new_privs`), `process.rs` (`Env`: the variables a command runs with, the place's else the process's, less the hidden ones; its own session with no terminal, a deadline, a stop, both pipes read on threads, the group killed, then the rest of the session), `sweep.rs` (every process of a session killed by its session id, on macOS listed into a table on the stack, on Linux the numbered entries of `/proc`; called from ordinary threads only), `inherit.rs` (`streams_only`: what a command inherits of llx, its standard streams and no other descriptor, every one above stderr marked close-on-exec between fork and exec; for `bash`, monitors and the daemon) and `output.rs` (head and tail kept, about 40,000 characters a stream, the middle cut).
  - `ask.rs`: `AskTool`, the agent's `ask`: one to three questions, read leniently, answered through `Person`.
  - `testing.rs`: test-only: temporary directories, and a gate that records what it is asked.
- `packages/providers/`: the models' providers, a package each, told who calls them (`App`).
  - `kit/`: what they share, with no port: `http.rs` (`Http`, a POST answered with a status and a body; `Web` on the OS's TLS; forms and queries), `oauth.rs` (PKCE, random state, a pasted redirect, a token's claims, opening the system browser), `loopback.rs` (the sign-in callback on 127.0.0.1: route and `state` checked, `/cancel` to give way), `page.rs` (the browser's success and failure pages), `store.rs` (credential files, 0600; a pasted key read, a key masked for showing), `sse.rs` (server-sent events), `retry.rs` (a request asked again when a wait may mend its answer, never one that went out unanswered unless the caller says so), `cache.rs` (the prompt cache's key: a hash of the start every session's requests share).
  - `models/`: the model catalog, the one source of model facts (MODELS.md): `data/` is models.dev's own files for the popular providers (`scripts/models_sync.py` copies them from a clone), `build.rs` resolves them as models.dev does into its v2 shape (built in deflated, and read only when no fetched catalog has the provider asked for), `lib.rs` types it (providers, chat and decision models, windows, levels and defaults, API addresses; `takes_lark`, which a fetched catalog answers from the built-in files, as models.dev's API does not publish it), `provider.rs` (a provider read as an index of raw JSON, each model decoded the first time it is asked for: a run decodes the few it uses), `source.rs` fetches models.dev's v2 API at most once an hour (ETag) and keeps it in `<config>/models.json`, over the built-in files. `types.rs` is the catalog's types: a model as models.dev's v2 publishes it, and what its facts say (its price, its API's address).
  - `openrouter/`: `chat.rs` (chat completions, tool calling; OpenRouter's `reasoning`, cost and prompt-cache marks, or `reasoning_effort` for any other OpenAI-compatible host, and OpenAI's own API the prompt cache's key), `system_one.rs` (the decision models), `client.rs` (OpenRouter, or any address the catalog gives; the kit's `retry`: a timed-out request is not sent again, but a decision is, once), `auth.rs` (the OpenRouter key's variable, its credentials path and the PKCE sign-in; saving a key is `Provider::save_key`, for every provider).
  - `openai/`: a ChatGPT sign-in: `auth.rs` (the OAuth flow: authorize, exchange, refresh), `tokens.rs` (the tokens, the account id from their claims, `openai.json`), `responses.rs` (the chat port over the ChatGPT backend's Responses API, streamed; each conversation a session of its own at the backend (`session-id` and the prompt cache's key, from its first words), so sessions and agents reach their own cache and no one machine takes them all; refresh before expiry and once on 401), `responses/offer.rs` (the tools as the backend takes them: `apply_patch` a custom tool held to its Lark grammar where the catalog says the model takes one (`Texts`), else a function), `responses/route.rs` (sticky routing: the `x-codex-turn-state` a task's first reply names, sent back with the task's later requests so they reach the machine that holds its cache).
  - A new provider is a package here implementing `Chat` (and `Decider` where it has decision models) with a catalog, and one arm per `match` in `apps/cli/src/providers.rs`.
- `packages/protocol`: what the interface and the server say to each other (ARCHITECTURE.md W1-W8), wire types only, no workspace package: `event.rs` (`Event`: what happened in a session; a call's `Label` and `Outcome`), `asked.rs` (`Asked`: a question for the person, a choice's rows in optional `Group`s; `Reply`), `command.rs` (`Command`: what the interface asks of the server, `Done`; `Place`, where a client is: its directory and environment, given at `Initialize`), `frame.rs` (`ToClient`, `ToServer`: every frame, `resource/verb` named, the same in process and over a socket; an event's `seq`, `Gap`; `Command::Attach { cursor }`, `Done::Attached { seq }`).
- `packages/client`: the interface's side of the seam: `Client` (`in_process` over channels; `connect`, over a socket in `socket.rs`: a frame per JSON line, a writer thread, the same reader loop), `call` waits for what a command came to (`CallError`: gone, timeout, failed), `send`, `reply`; every other frame goes to the interface as it comes. Only `protocol`. `place.rs`: `here`, where this process is, as the interface says it at its handshake.
- `packages/queue`: one queue for what reaches a run from outside its own calls: entries with their own policy (whether a running task takes one, and what becomes of it while none runs: `Idle::Opens`, which waits for the next task when nothing opens it, or `Drops`), bounded, rendered as tagged data. No workspace package.
- `packages/session`: a history store: sessions as JSON files.
- `apps/cli`: the `llx` binary and the composition root.
  - `main.rs`: where the process exits, with the code the run returns.
  - `hardening.rs`: what the process does once at its start to keep what it holds (the provider's key, in its environment) from the user's other processes, the agent's commands among them.
  - `cli.rs`: the command line.
  - `commands/`: `run.rs` (a session or one `exec` task: checks, then the work; `At`: at this terminal, or `Served` by the daemon to a client) with `run/task.rs` (one task on the `Rig`: run, reported, recorded), `run/interface.rs` (the interface in process, `serving`: a server for one interface, the daemon's for each connection) and `run/remote.rs` (the session as the daemon's client), `run/ended.rs` (how a task ended: the report, the exit code), `serve.rs` (`llx serve`, the daemon: lock, socket, ready line, a desk per client from its place and command line; `status`, `stop`), `repl.rs` (a session's prompt, in the interface), `entry.rs` (what is typed at the prompt: the slash commands, the help), `login.rs` (`/login`: the provider and its sign-in, each a pick on a stack: Esc goes back one step, titled by its path; then `model.rs`'s steps), `model.rs` (`/model`, each provider's models a group, the reasoning level, Shift+Up/Down; a choice put in, its key's variables kept from commands, saved), `signin.rs` (signing in to each provider, and `logout`), `sessions.rs` (`sessions`, `resume`), `doctor.rs` (the shell checked through `tools::shell::shell`, the one `bash` runs), `rewind.rs` (`/rewind`), `extras.rs` (`/diff`, `/init`, `/copy` (the text sent as `Event::Copy`), `/usage`). `decide.rs`: `llx decide`, one question about stdin to the decision model, the option it picked alone on stdout.

  - `choice.rs`: the provider, model and level a run uses (the options, else what `/login` saved in `settings.json`). `live.rs`: `LiveChat`, the model a session thinks with, switched by `/login` between tasks.
  - `picker.rs`: `Picker` (a title and items in, an index or a cancel out) and `Lines`; the interface implements both.
  - `agents.rs`: `agents`, the tool that starts other agents, and the `Registry` it shares with their threads (scoped to the session in `compose.rs`): each a session whose parent is the main one, with the same context and gate, a stop of its own, and neither `agents`, `ask` nor `jobs`.   - `jobs.rs`: `jobs`, monitors and schedules: what comes back goes to the task running, else to the interface as a task of its own. the scheduler sleeps until the soonest schedule is due or a schedule is added, stopped or the session ends (its `Bell`); `jobs/monitor.rs` (a command started and killed as the tools' `shell` does, in a session of its own, lines in batches, its stop and deadline kept after it closes its output), `jobs/cron.rs` (5-field cron in local time, delays), `jobs/spec.rs`.
  - `meta.rs`: what is known of a session beside its tasks, as it changes (`Update`: its title now, more fields later), reaching the interface as `Event::Updated` and the saved session through `Pending` (applied before each of the lane's saves, written at once to a session on disk, under one lock). `meta/title.rs`: the title, asked of the same model at its lowest level on a thread of its own when a session's first task starts; the task never waits for it.
  - `arrivals.rs`: the one table of what reaches a lane's run (an agent's answer, a monitor's lines, a schedule), each kind's policy and tag, and the lane's queue.
  - `checkpoints.rs`: each task's goal and where it began in the conversation, for `/rewind`.
  - `compose.rs`: builds the model, then (`assemble`, testable with fake models) the mode's gate and the person, then (`equip`) the tools, the agents, the jobs and the inbox, then the `Agent`; `Rig` switches the mode and tells the agent of a change. With `compose/setup.rs` (`Setup`, what the lanes share, a lane's `Seat`), `compose/lane.rs` (a lane's models, stop and output) and `compose/rig.rs` (`Rig`, built by `drive`, which runs the work with it).
  - `context.rs`: the environment block, the instructions (`gather`), an earlier session (`resumed`); one message, the same all day, cached.
  - `instructions.rs`: `~/.llx/AGENTS.md`, then per directory `AGENTS.override.md`, `AGENTS.md` or `CLAUDE.md` with `@imports`; a subdirectory's file the prompt says to read before working there.
  - `attach.rs`: pictures attached to a message, read for the model (the paths the interface sends, `--image`).

With `host.rs` (`Host`: the daemon itself, its build, its clients and what is open: `Status`, `Shutdown` (a `Bell`), a client of another build refused). `work.rs`: what runs in the lanes, as their events say it (`busy`), for the question asked before quitting.

  - `error.rs` (`Failure`) and `exit.rs` (the exit-code contract).
  - `testing.rs`: test-only helpers.
  - `tests/all.rs`: the one integration-test binary. `common/`: a home per test, a scripted model (`Reply::Call` is one call), a pseudo-terminal read through `vt100` (a session there runs in a daemon of its home, stopped when the test ends: `home::stop_daemon`). `suite/`: the binary end to end, with no network (`suite/tui/`: flows at a real terminal); `suite/repo/architecture.rs`: the layer rules; `suite/repo/core.rs`: the core names no effect (C1); `suite/repo/budget.rs`: the size budget.
- `evals/`: live coding tasks (fixtures in `evals/fixtures/`). `benchmarks/` (written by `run.py --record`): their history.
- `scripts/`: `check` (the checks' one entry point, below) with `checks/`: `plan.sh` and `plan.awk` (the checks a change needs, from its paths), `run.sh` (each check's command), `tree.sh` (the changed paths, the tree's fingerprint and stamp), `tools.sh` (the pinned linters), `mdlinks.sh` (Markdown's relative links), `check_test.sh` (their tests); `hooks/` (git's `pre-commit` and `pre-push`, Claude Code's `claude-stop`, wired in `.claude/settings.json`), `setup` (the git hooks installed), `ci-docker` (CI's jobs in Docker: each job's `run` steps read from `ci.yml`, in `docker/Dockerfile`'s image of the runner); the release scripts (`dist.sh`, `npm-pack.sh`, `release-notes.sh`, `install.sh`), `coverage.sh`, `models_sync.py`.

## Rules

Layers (checked by `apps/cli/tests/suite/repo/architecture.rs`):

- L1: `contracts` depends on no workspace package.
- L2: `agent` depends only on `contracts`.
- L3: tools and stores (every other package under `packages/`) depend only on `contracts`; primitives the app composes (`queue`) on no workspace package; providers (under `packages/providers/`) only on `contracts` and the provider kit, which depends on no workspace package. A tool knows nothing of the agent, the models or the other tools. A provider knows nothing of tools or of the other providers.
- L4: only apps compose packages. Nothing depends on an app.
- L5: `contracts` and `agent` name no tool or provider: no browser, page, URL, OpenRouter, OpenAI, model name. The agent learns what a tool's world is like through `ToolSpec::description`. Where the run happens (the directory, the system, the mode) reaches the agent through the app's context.

Behaviour:

- A tool asks the `Gate` before an effect outside the conversation: a changed file, a command. The `Effect` summary is one line the person can judge, and it leaves nothing out (the whole command, the directory it runs in). A `Deny` goes back to the model as a failed call with its reason. Only the app answers the gate (`apps/cli/src/mode.rs` and `gate.rs`); a tool never decides its own approval. A `ReadOnly` verdict runs the command in the system's sandbox, where it can change nothing, and refuses it where there is none (B3).
- A tool asks the person only through `Person`; only the app answers it (`apps/cli/src/server/asking.rs`), never in `exec`. A mode is a named set of rules (ARCHITECTURE.md K5): it changes only what the gate answers and the context's `Mode:` text, never filters tools, and no code branches on its name. Rules come from the command line and the person's settings, never from the repository.
- A path the model wrote (a command's `workdir`) goes through `Workspace::readable`. Never open one without it.
- Tool content (files, command output) is untrusted data. Never let it reach a request as an instruction; mark it so where the agent reads it.
- No task- or site-specific wording in the agent's prompt or the tool descriptions. A rule earns its place by the evals, and stays general.
- Synchronous code: threads where needed, no async runtime. Tools, gates, the chat model and the person are `Send + Sync`: a turn's calls and the agents run on threads.
- The release binary stays small (under 4 MB). No dependency that is not already in the tree unless it earns its size; std first. Check `scripts/check --only size` after adding one: it fails above 5 MiB (CI's size job runs it) and warns above 4 MB.
- Exit codes (`apps/cli/src/exit.rs`) and the `--json` events (`apps/cli/src/output/json.rs`, `SCHEMA`) are a public contract. Change them only with a schema bump and a CHANGELOG entry.

Code:

- Unit tests live beside the code, never inside it: `x.rs` ends with `#[cfg(test)] #[path = "x_tests.rs"] mod tests;` (checked by the architecture test). Fake the ports (a scripted `Chat`, a `Gate`, a `Decider`, a `View`) instead of calling a network.
- One module layout (ARCHITECTURE.md S6): a module with children is `x.rs` beside its directory `x/`, never `x/mod.rs` (clippy's `mod_module_files`). The integration tests keep `tests/common/mod.rs` and `tests/suite/mod.rs`, as cargo needs: a `tests/x.rs` is a test binary of its own.
- Every file holds at most 300 lines of working code (ARCHITECTURE.md S1, checked by `budget.rs`): a file about to pass it is split by what it does first. rustfmt defaults. Comments explain why.
- The workspace's lints are hard (`Cargo.toml`, `clippy.toml`; ARCHITECTURE.md S4): no `unwrap`, `expect`, `panic!` or `unreachable!` in working code, no prints outside the output, no `process::exit` but in `main.rs`, no `Rc`/`Cell`/`RefCell`, functions at most 100 lines, `pub` only across crates. Our own enums are matched exhaustively, no `_` arm (S10); a struct's fields are all bare `pub` or none, another crate reading a private one through a method (P3); `write!` into a String, not `push_str(&format!(..))`; a default built lazily (`unwrap_or_else`, `map_or_else`); `clone_from` over a value already there; `sort_unstable` for primitives; a parameter only read is borrowed; a method returning a changed copy is `#[must_use]`; no dependency left unused (the clippy checks). Never turn a lint off in `Cargo.toml` or for a whole module to get a change through: handle the case; the exception is an `#[expect(lint, reason = "...")]` on the smallest item, never an `#[allow]` (an exception that no longer applies fails the build); one that fires on one system or build only goes under `cfg_attr`, and a foreign enum's `_` arm names the enum in its reason. `unsafe` only in `tools` and the apps (S5).
- The project stays under 50,000 lines of working code (`apps/cli/tests/suite/repo/budget.rs`; build scripts count; tests, comments and blanks do not). This is the maximum. New code is paid for first by cutting or simplifying existing code. If a change still cannot fit, stop and ask the owner before going over: say how many lines it needs, what was already cut, why the rest cannot be, and the alternatives. Never raise the limit on your own.
- English only, in code, comments and docs.

## Tests first (TDD)

Every change is red, green, refactor:

- A bug: first a test that reproduces it, at the layer where a person meets it, run and seen failing for the right reason; then the fix; then the test passes. The red run is the proof the test can fail: never break working code to get one.
- A feature or a change of behaviour: its tests first, written from what a person does and sees (keys pressed, the screen, what the model was sent), then the code.
- Refactor only on green. A test that cannot fail, or that restates a text or a constant, is deleted, not kept.

The layers:

- unit tests beside the code (`x_tests.rs`), with the ports faked;
- screen tests in the crate: the `App` driven by keys and events and drawn into a `vt100` screen (`apps/cli/src/tui/test_support.rs`), asserting what the screen shows, never the app's fields;
- one integration binary, `apps/cli/tests/all.rs` (`common/` for the harness, `suite/` for the tests): the real binary against a scripted model server that keeps every request (assert what the model received), and pty flows in `suite/tui/` that press keys and read the screen as a person does.

## Checks

`scripts/check` is the one entry point, and the same commands run everywhere: by hand, in the git hooks, in Claude Code's Stop hook, and in CI (each step of `.github/workflows/ci.yml` is `scripts/check --only NAME`). It prints a plan (each check, its scope, why), runs it in one fixed order, stops at the first failure with that check's output, and ends with one summary line; exit 0, 1, or 2 for a usage error. `scripts/check --list` names the checks, `--plan` prints the plan for the paths on stdin.

What runs when:

- Before you say a change is done: `scripts/check`. The checks the branch's change needs: everything changed since the merge base with main, plus the working tree (staged, unstaged, untracked).
- When a Claude Code agent ends its turn: `scripts/check --fast` (`scripts/hooks/claude-stop`, in `.claude/settings.json`), only when the working tree changed since a check last saw it (a stamp in `target/llx-check/`), so an unchanged tree costs nothing. A failure blocks the stop with its output; the same failing tree is let through the second time, with a note. It changes no file and stops after 240 s. `LLX_STOP_CHECK=off` turns it off.
- `git commit`: `scripts/check --fast --staged` on what the commit stages (a staged file with unstaged edits is refused: the checks read the working tree). `git push`: `scripts/check --fast` on what is pushed (since the remote's commit), in seconds; the tests, the size and the site run in CI, and by hand with `scripts/check` before a change is called done. Install both once with `scripts/setup` (`git config core.hooksPath scripts/hooks`); `--no-verify` skips them.
- CI: every check, a job for each group (`check`, `size`, `site`, `action`). `scripts/check --all` runs the same set locally, in CI's order; add `--coverage` before a release.

The plan comes from the changed paths alone (`scripts/checks/plan.awk`, with an example of each rule in `scripts/checks/check_test.sh`): a crate's directory brings `fmt`, `clippy` and `test` for the crate and its dependents (cargo metadata's graph; `--fast`: clippy on the crate alone); the root `Cargo.toml`, `Cargo.lock`, `clippy.toml` or `rust-toolchain.toml` the same for the workspace; a manifest, the lock or the toolchain the release `size`; anything the repository's rules (`repo`: `suite::repo`, unless the tests run them); `site/`, `docs/` or `examples/README.md` the `site` build; `action.yml` or `action/` the `action` tests; a shell script `shellcheck`; a workflow, `action.yml` or an example `actionlint`, and an example the `examples` conventions; Markdown, or a path gone, `mdlinks` (relative links and anchors). `--fast` leaves out the tests, the size and the site. The linters are pinned (shellcheck, actionlint, yq, jq in `scripts/checks/tools.sh`): downloaded once into `~/.cache/llx/tools`, each checked against its SHA-256, never the one on the PATH.

Ratchets: the line budget and the 300-line files (`budget.rs`), the `expect`s in working code, which only fall (`code.rs`, S4), the coverage floor (`scripts/coverage.sh`), and the binary's cap (`size`: fails above 5 MiB, warns above 4 MB).

What the checks run (`scripts/checks/run.sh`), and the rest by hand:

```bash
cargo fmt --all --check                                       # fmt
cargo clippy --workspace --all-targets -- -D warnings          # clippy
cargo clippy --workspace --lib --bins -- -D warnings -D unused_crate_dependencies  # then: no dependency unused (tests left out)
cargo test --workspace            # test: unit tests, apps/cli/tests/all.rs (the binary, the layer rules)
cargo test -p llx --test all -- suite::repo::                  # repo: the repository's rules alone
cargo nextest run --workspace     # the same tests under cargo-nextest
scripts/coverage.sh               # coverage: line coverage with cargo-llvm-cov; fails under 85% (raised with coverage, never lowered)
cargo build --release             # size: target/release/llx under 5 MiB, warned above 4 MB
python3 evals/run.py --repeat 3   # live, paid; run for agent, prompt, tool or loop changes
python3 evals/run.py --only code  # the coding tasks alone
```

- The log, `~/.config/llx/logs/llx.log`: what every llx process did, the daemon's too (each call with its arguments, each failure, each task's end); `RUST_LOG=llx=debug` adds the model's turns and words, `RUST_LOG=off` keeps nothing.
- `llx -v` shows each tool result and model turn in the trace.
